## v0.3.9：分页界面与 DIY 武器页（2026-11-22）

主窗口改为 `QTabWidget` 两页，第一页保留全部自动拾取、千刀、筛选、统计与日志，第二页是 DIY 武器。只有工具栏、状态栏和菜单是共用的，两页之间互不影响；日志仍集中在第一页，DIY 的操作与错误也写进同一份运行记录（事件列显示「DIY 武器」）。

武器目录完全离线生成，不需要注入进程：`tools/build_weapon_catalog.py` 直接读 `ph_ft/source/data0.pak` 的 `scripts/inventory/*.scr`，再读 `data_lang/datacn.pak` 里 `texts/pc/pc_cn_lang.binsloc` 的 `m_keys` / `m_Values` 两张字符串表，产出 `beast_pick/data/weapons.json`。条目字段：`n` 名称、`kind` 近战/枪械、`sub` 子类、`s` 由 `WEAPON_FIELDS` 抽出的属性、`tbl` 伤害档位表名、`q` 品质索引、`mods` 可装槽位。生成的目录包含 **2,735 个武器定义（近战 2,059 / 枪械 676）、114 个配件、83 条词条、72 张数值伤害档位表（另有 38 张公式表单独存放）**；1,983 个定义关联到 `damagedefinitions.scr` 的伤害档位表。定义里有大量 `_r1`–`_r15` 等级变体，同一把武器因此重复几十次；`diy.families()` 按「名称 + 类型 + 子类 + 伤害表 + 品质」归并出 **176 种武器**，取最高等级带作为代表条目并保留全部变体 ID，`variant_index()` 负责把游戏里读到的任意变体映射回代表条目。

伤害表里同一个 `Damage("x_N")` 块按三种写法出现，必须分开处理，否则会得出荒唐数值：

- 固定值：`Cut("58")`，直接取数。
- 带倍率：`Cut("110.0 *0.01")`，乘上去才是真实系数。
- 区间：`Cut("11 - 12")`，取中值 11.5，界面上按单一档位展示。
- 公式：`Cut("1%-101% of MaxHealth")` 属于脚本 NPC、剧情道具和部位伤害，没有固定数值。过去按「取开头数字」会把它们变成「1 点伤害」，现在整张表移入 `special`，预览显示公式原文，并在测试里断言没有任何玩家武器引用这类表。


本地化取值有三类坑，都在生成器里处理：

- 文案里带渲染标记（`%COLOR(...)`、`%COLOR_END`、`%IMG(...)`），显示前必须剥掉，否则会直接出现在名称里。
- 嵌套引用 `&key&` 最多递归 16 层；解析失败时退回定义本身而不是留空。
- 中文本地化没有覆盖的内部分支（`_Coop_Base`、`Fury_*` 冲击波、`*_Invisible` 随机配件、Outfit 曲线词条）不属于玩家在菜单里能选的东西，直接不进目录；剩下的名称若仍无译文，用标识符拆词兜底，不留原始下划线 ID。

配件名称在 T1–T4 之间重复（同名的「伏特之力」有四档），所以下拉框用 `n + 档位/品质` 组合显示，词条则对 `_Coop_Base` 变体加「（联机）」后缀。

DIY 页的校验与预览（`beast_pick/diy.py`）是纯函数，不接触进程，可脱机单测：品质取 0–6、档位受该武器伤害表长度约束、9 项属性各有上下限、配件必须能装进所选的槽位、词条最多 8 条且去重。预览把伤害表命中值乘以配件 `CraftingEffect_IncreasedDamageMul` 得到合成伤害；同一配件里完全相同的 `Effect(key, value)` 只计一次，避免把重复声明算成双倍加成。

配件插槽按生成目录保留的 `CraftingSlots` 处理：只显示该定义开放的插槽，方案校验同时检查武器是否支持该插槽、配件是否能装入该插槽。挂饰详情使用原始品质和 `UIStat` 显示值、单位；完全重复的条目只显示一次。「读取手上武器」已移除。

引擎只能在模拟线程上访问，而同步 RPC 无法返回 Promise，若让 JS 运行时阻塞等结果会直接死锁。所以已有的 `diyApply` 只负责排队并立即返回，结果通过 `diy` 事件回推；3 秒未执行会主动回报超时，界面侧另有 4 秒兜底定时器。

**写入已开放（7 项属性）。** 标定结果写在 `profiles/current.json` 的 `diy` 段，全部来自实测而不是猜测：

- 属性块不在 `AVInventoryItem` 本体里——`item + 88` 只是指向描述对象的指针，真正承载属性的是**内嵌描述对象的那个容器**，即 `desc - 0x58`。第一版把偏移按 `AVInventoryItem` 算，写进去的是无关字段（已回滚为 0）；按 `desc - 0x58` 重算后，`desc.sub(88).add(0x304)` 才对应伤害浮动。
- 容器里同一份属性块有 **3 份副本**，步长 `0x498`（1176）。写入时三份一起改，避免 UI 与战斗计算读到不同副本。实测 `0x304` 伤害浮动、`0x310` 物理倍率、`0x31c` 重击倍率、`0x360` 耐久（CriticalCondition）、`0x364` 伤害范围、`0x398` 耐力伤害、`0x488` 耐力消耗，与目录里同一武器的 `DamageRange=1.35`、`PhysicsDamageMul=2.5`、`PowerAttackDamageMul=0.5`、`CriticalCondition=30`、`DamageSize=3`、`StaminaDamage=273`、`StaminaUsage=0.396` 逐一对应，写入 5 秒后仍保持，说明是实例存储而非每帧重算的缓存。
- 暴击率、暴击伤害、击晕几率在这份块里没有出现（目录值为 0/2/0，`2.0` 在整块里搜不到），它们来自别处（很可能是定义侧的曲线），所以界面把这三项置灰为只读。
- 品质与档位由武器定义决定：目录里 `wpn_1hs_axe_03_green_*` 与 `_baron_*` 是不同定义，实例属性块不存品质。改品质等于换定义指针，但定义对象没有可用的导出入口（见下），因此品质、配件、词条暂不写入。
- 写入路径：`diyApply` → `queueDiy('apply')` → 模拟线程里 `equippedParts()` 取描述对象 → 按 `diy.stats` 偏移写 float → 回读 → `send({event:'diy', kind:'apply', applied, skipped, verify})`。界面把 `verify` 写进日志，消息里说明哪些字段没写。
- 偏移只对 `ItemDescMelee` 成立：`diy.desc_type` 声明标定所属的描述类，`applyDiy` 写入前比对 `type(desc)`，不匹配直接拒绝（枪械内嵌的是另一个描述类，同样的偏移会落到无关字段）。界面侧 `diy.writable_for(entry)` 用同一份声明决定属性框是否可勾选。
- 反馈闭环：任何一次点击都必须有结果——条件不满足时 `DiyPage.blocked` 冒泡到主窗口，同时写运行记录、更新结果条并弹窗；按钮不再按连接状态置灰，避免「灰色按钮点了没反应」被误判为卡死。

字段布局的调查结论（`artifacts/diy_fields_probe.js`、`artifacts/diy_vtable_probe.py`、`artifacts/diy_export_scan.py`，均只读）：

- 引擎导出了 `?GetFields@CRTTI@@` 与 `?GetName@CRTTIField@@`，也就是说只要能拿到某个类型的 `CRTTI*`，就能列出它的字段名和偏移（`CRTTIField + 0x50` 是偏移）。这是唯一一条不需要逆向函数体的字段来源。
- 但 `CRTTI*` 拿不到：`engine_x64_rwdi.dll` 的 45,776 个导出里只有 2 个 `??_7` 虚表，且都不是物品类型；没有 `?GetRTTI@ItemDesc*` 这类静态入口，也没有 `CRTTIManager` 单例 getter。`gamedll_ph_x64_rwdi.dll` 只有 9 个导出，物品工厂与生成器同样不在导出表里。
- 因此唯一可行的入口是「有存档时从活对象反推」，这也是最终采用的办法：不解析 `CRTTI`，而是拿手持武器的描述对象，按目录里已知属性值做**数值指纹匹配**——在对象里搜 `1.35`、`2.5`、`0.5`、`30`、`3`、`273`、`0.396` 这些该武器独有的组合，一次就锁定整块偏移。纯 getter 扫描（`mov eax,[rcx+off]; ret` 这类模式，见 `artifacts/diy_getters_probe.js`）只找到 12 个字段，不足以覆盖属性，仅作为交叉验证。

## v0.3.7：修复自更新后的 Python DLL 启动失败（2026-11-07）

PyInstaller 单文件程序自更新时，旧进程会把 `_PYI_*` 和 `_MEIPASS2` 运行时变量传给更新助手；助手再启动新版时，新 bootloader 可能继续引用旧版已经清理的 `_MEI` 目录，最终显示 `Failed to load Python DLL`。更新助手现在清理这些变量并设置 `PYINSTALLER_RESET_ENVIRONMENT=1`，新版启动前再次执行同样的隔离。这样每个版本都会创建自己的运行时目录。

## v0.3.6：尸体批量领取与快速重试（2026-11-07）

尸体和状态 1 的普通容器仍复用游戏自己的逐项领取入口，但同一模拟线程回调会连续处理最多 16 件；每次调用后重新读取物品向量，适应游戏即时压缩索引的行为。当前构建在 `full+0x4C8` 保存可领取描述，`full+0x4D8` 是与其同步变化的并行 bookkeeping 向量；官方逐项入口只接受 `0x4C8` 的索引，实测两组计数同步减少，因此继续以描述向量做筛选不会漏掉第二组独立物品。这样不会跨线程并发调用原生函数，也不会保存下一轮使用的原生指针。新出现的尸体在候选排序中优先处理。

交互暂时不可用时采用 0.25、0.5、1、2、4 秒的退避（上限 5 秒），避免旧的 2、4、8、16、30 秒退避把刚生成的尸体拖到很久以后。回归测试覆盖同一回调内批量领取、索引刷新和快速重试。

## 本地交付记录：箱柜开启与详细筛选（2026-11-01，更名前）

本节为当前行为，取代下文历史记录中的“不提供自动开箱”。用户后续明确要求重新加入箱柜和锁箱开启，门仍排除。

- 精确物品身份：ItemDescWithContext+8 指向定义；定义 slot99 必须为游戏 RVA 0x254530，定义+8 为 ttl 字符串，支持内联短串和指针字符串。与目录的 ID、大类共同核对后取得中文名和子类；仅缓存纯元数据。
- 目录提取 inventorystuff 枚举、inventory 脚本和中文 binsloc。重复 Item 声明合并，防止后面的局部覆盖丢失 Name/ItemType。当前 4077 个 ID、71 子类；未知中文名显示内部标识。
- 本地化名称中的嵌套 &key& 引用继续解析；未解引用、循环或超深引用退回真实物品 ID，避免筛选列表直接出现模板占位符。实际耐力强化剂、恢复强化剂名称已核验。
- 规则为 item_rules.items 与 item_rules.subtypes 的显式布尔映射，缺省继承；优先级物品 > 子类 > 大类。尸体和 Container 始终用当前索引逐项领取；未知身份有精细规则时跳过；有排除项时不领不透明包。
- 开启仅允许精确 Container / ComplexContainer，状态2，正常启用并通过 can-use action7；必须匹配196/197虚表入口。Container 有关联触发器时跳过。ComplexContainer 的 m_ForceNoLoot / m_LockpickDifficulty 字段必须反射验证，字段偏移分别1176/1008，相对 CRTTIObject slot6 返回的数据基址（实测 full+0x20），并非 full。

## 原生调用

- `ILevel::FindObjectsInRadius` 返回 IControlObject；通过运行时类型识别 BodyContainer、Container、ComplexContainer、DroppedItem、ContainerItem。
- 当前构建 IGame 虚表 151、152、153 用于角色变换、玩家实体列表、本地玩家实体；由本地实体取得实际玩家对象。
- 所有游戏查询和领取统一在 `IGame::GetGameTimeDelta` 的指定模拟更新调用点运行（引擎 RVA 0xBC3D22），不从 Python 工作线程直接调用领取函数。
- BodyContainer：检查启用标记、状态 1、非空物品向量；调用已观察到的初始化与 ILootable 领取入口。返回成功且物品向量减少才计数。
- DroppedItem / ContainerItem：复用本地玩家当前交互上下文，先调用正常可使用判定，再调用领取；清除交换标记，不使用 G 换装。下一次范围查询确认目标消失后才计数。
- Container：只处理状态 1/2、启用标记正常且 full+0x570 没有附属脚本触发器的对象。虚表 196/197 必须匹配 0x1121810/0x1194280；状态 2 先正常 can-use/execute action 7，下一轮重新查询。状态 1 先正常 can-use action 1，再调用该类 init 0x118B190 与共用 ILootable 逐项领取，不强写状态。使用与尸体相同的 CategoryType 过滤和向量减少确认。
- ComplexContainer：仅状态 2 且散落物品功能已启用时尝试打开；虚表 196/197 必须匹配 0x1121730/0x1193F50。正常 can-use/execute action 7 后确认状态 1，仅记为打开；下一轮查询生成的 ContainerItem，按现有筛选领取并确认消失。不把“打开”计为内容已经领取，不缓存子物品指针，不执行开锁动作。

## 持续运行

默认半径 8 米，按用户反馈扩展为可调 1–500 米，仅能查询到游戏已加载的目标。每 0.3 秒重新查询（扫描耗时上升时自动放缓，最大间隔 1.5 秒），每轮至多处理 3 个目标；每具尸体或普通容器在一次模拟线程回调内最多连续领取 16 件。不会保存下一轮需要执行的原生指针。失败按 0.25、0.5、1、2、4 秒退避（上限 5 秒）；搜空的尸体不再领取。远距离领取尚需结合实际场景验证。

暂停、加载、失去前台、本地玩家未就绪、玩家实体数不为 1 时等候。新场景需稳定后才查询。Python 心跳超过 5 秒没有更新即关闭功能。关闭窗口卸载钩子并断开。
